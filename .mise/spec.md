# Spec: per-branch diff base, notes from the pane, responsive marks

## What

- **Per-branch diff base.** Each branch has its own diff base, shared by every worktree on that branch. Resolution order: explicit base (set in the status-bar picker or by an agent through a documented contract file), else auto-detected (closest local branch HEAD forked from, else a differently-named upstream), else the `deltaReview.baseBranch` setting (default `main`). A new status-bar item `$(git-compare) ← <base>` opens the picker; its tooltip names the source. A stored or detected base that is fully merged into the fallback raises a Switch / Keep / Choose… prompt, never a silent switch. An explicit base that no longer resolves shows a tree message linking to the picker. `delta:cluster` computes the same base.
- **Notes from the pane.** A `+` in the Review Notes title bar offers "File note" (whole-file thread at the top of the active file's diff; disabled with a reason when the active file is not in the diff) or "General note" (no file; opens its own conversation tab). General notes group above file groups; file notes sort first in their file group and show `file` instead of `:<line>`. Notes file goes to version 3; the review-notes skill documents both kinds.
- **Responsive marks.** Mark/unmark updates the row, badge and counter immediately; a failed write rolls back with an error offering Retry and Show Log. The extension's own review-ref writes no longer restart the refresh debounce; the debounce gets a max wait; `refs/review/<branch>` and `refs/review-predeletion/<branch>` writes use compare-and-set with retry; the silent no-ops of the mark commands report why.

## Design

### Per-branch diff base

- **Contract file** (agent-settable, extension-written): `<git common dir>/delta-review/base-<sanitized-branch>.json`, `{ "version": 1, "branch": "<branch>", "base": "<ref>" }`. `base` is any ref `git rev-parse --verify "<ref>^{commit}"` accepts. Sanitization is `sanitizeBranchForFilename` (`src/clusters.ts:234`), which maps different branches (`feat/x`, `feat-x`) to one file name, so the file records its owning `branch` (the full name, no leading `heads/`). Present with a matching `branch` = explicit base. Absent, or present with a different `branch` = automatic (no error). Invalid (bad JSON, wrong version, `branch` or `base` not a non-empty string) = treated as absent, with the parse error in the base item tooltip. The extension overwrites it (whoever owned it) only on a user pick, Switch or Keep, and deletes it only on "Use automatic detection", and only when the file is invalid or its `branch` matches. Writes are atomic: temp file in the same dir, then rename. The existing contract-dir watcher (`{*.json,...}`, `src/extension.ts` `watchContractDir`) already refreshes on its changes. Collisions: two branches whose names sanitize alike share one file; the last writer owns it and the other branch reads it as absent (automatic). The contract is owned by `plugin/skills/cluster/SKILL.md` (new Contract section "Diff base").
- **Detection** (`src/diffBase.ts`, vscode-free):
  - Every function taking a branch first strips one leading `heads/` (`readMarkBranch`, `src/pendingRead.ts:19-20`; `rev-parse --abbrev-ref HEAD` prints `heads/<name>` when a tag shares the name). The stripped name is used for the contract file, the reflog ref, the `branch === fallback` check, candidate exclusion and `BaseResolution.branch`.
  - When the branch is the fallback itself (or detached), detection is skipped and the source is `fallback`: on `main` no feature branch is ever picked as base.
  - Candidates and distances come from one spawn: `git for-each-ref --format='%(refname:short) %(objectname) %(ahead-behind:HEAD)' refs/heads` (git >= 2.41), in output (refname) order, excluding the current branch. `ahead` = commits in the candidate not in HEAD; `behind` = commits in HEAD not in the candidate (= `rev-list --count <c>..HEAD`), which is the distance.
  - The current branch's own reflog is one more spawn: `git reflog show --format='%H %gs' refs/heads/<branch> --` (newest first; shared by all worktrees). From it:
    - `creationRef`: the oldest entry's subject `branch: Created from <ref>`, with a leading `refs/heads/` stripped, when `<ref>` is not `HEAD`.
    - `unmoved`: the newest entry is that creation entry and its sha equals HEAD's (the branch has no commits of its own yet).
    - `ownCommits`: shas of entries whose subject starts with `commit`, `cherry-pick`, `revert` or `rebase`, or starts with `merge`/`pull` and does not contain `Fast-forward` (commits made on this branch), except a `… (finish): … onto <sha>` entry (`rebase`, `rebase -i`, `pull --rebase`) whose own sha equals its `onto` sha: that rebase replayed nothing, so its sha is the new parent's tip, not an own commit.
    - No reflog (disabled, expired, failed read) means no `creationRef`, `unmoved` false, empty `ownCommits`.
  - Skip a candidate when:
    - `behind == total`, where `total = git rev-list --count HEAD` (no common history);
    - `behind == 0` (its tip equals HEAD or HEAD is its ancestor) unless the branch is `unmoved`: a branch made from the current tip (`git branch x`, `git worktree add -b x`) or a child that merged this branch never wins, while a brand-new branch still detects the parent it sits on;
    - it is not the fallback and it contains any own commit (a child or a branch created at an own commit). One spawn, only when `ownCommits` is non-empty: `git for-each-ref --format=%(refname:short) --contains=<c1> --contains=<c2> … refs/heads` (git ORs repeated `--contains`), passing at most the 32 newest distinct `ownCommits` (newest first, so post-rebase shas are always included). This covers a child forked from this branch, whatever commits either side made afterwards, and a branch created at an own commit. A failed call skips nothing.
  - The smallest distance wins. A tie goes to the fallback name, then to `creationRef`, otherwise the earlier candidate keeps it.
  - With no candidate, use the upstream (`git rev-parse --abbrev-ref @{upstream}`) when it does not end in `/<current branch>` and `git merge-base <upstream> HEAD` succeeds.
  - Cost is fixed regardless of branch count or commits: for-each-ref and the upstream lookup on every call; `rev-list --count HEAD`, the reflog read, the `--contains` for-each-ref (only with own commits) and the upstream `merge-base` (only when the upstream is consulted) run only when the cache key (for-each-ref output + upstream + fallback) changes. The key includes the current branch's own line, so a new commit invalidates it. The cache is cleared on repo switch.
  - Older git (for-each-ref rejects `ahead-behind`): fall back to per-candidate `merge-base <sha> HEAD` + `rev-list --count <mb>..HEAD`, with per-candidate results cached by `candidate sha + HEAD sha`. `behind == 0` is `mb == HEAD sha`. Same skip and tie rules.
  - On a tie the fallback wins, so a merge-merged parent detects as the fallback, and a detected base is effectively never stale.
  - Known limitations (documented in DEVELOPMENT.md and the cluster skill): without a reflog (or when all of a child's shared own commits are older than the 32 newest), a child branch can win; a branch created at a commit this branch only fast-forwarded or reset to is not recognized as own; candidates at the same commit are indistinguishable except through `creationRef`; without a reflog a brand-new branch with no commits skips the parent it sits on and picks a farther ancestor until its first commit.
- **Resolution** returns `BaseResolution = { branch, base, source: "explicit" | "detected" | "fallback", detectedVia?: "forkPoint" | "upstream", fallback, missing: boolean, stale: boolean, fileError?: string, suggestions: { forkPoint?, upstream?, fallback } }`. `missing` is set when an explicit base fails `rev-parse --verify --quiet <base>^{commit}`. `stale` is true when the source is explicit or `detected` via `forkPoint` (never via `upstream`: `origin/main` lagging local `main` is not a merged parent), `branch !== fallback`, `base !== fallback`, base is a branch (`refs/heads/<base>` or `refs/remotes/<base>` exists), `git merge-base --is-ancestor <base> <fallback>` succeeds, and the base tip is off the fallback's first-parent chain: the last line of `git log --first-parent --format=%P <base>..<fallback>` has a first field other than the base tip's sha (empty output = not stale). The last rule keeps a parent with no commits of its own (its tip sits on the fallback's first-parent history) from reading as merged; the cost is that a base fast-forwarded into the fallback is never flagged (documented limitation). The result is cached by base sha + fallback sha.
- **Wiring.** `refresh()` (`src/extension.ts:405`) resolves the branch, then the base, then calls `computeReviewModel(git, resolution.base, …)`. `computeReviewModel` (`src/model.ts:574`) throws an exported `MergeBaseError` (`base` field, message `Cannot compute merge-base with "<base>".`) instead of the setting-hint text at `src/model.ts:606-608`. On a `MergeBaseError` the fatal path keeps the base item visible with the error tint and its picker command, and `treeView.message` comes from pure `mergeBaseErrorMessage(resolution)` (`src/diffBaseUi.ts`): source `fallback` keeps the setting hint (`… Check the deltaReview.baseBranch setting or click the base in the status bar to choose one.`), explicit/detected read `… Click the base in the status bar to choose another.`; context key `deltaReview.mergeBaseFailed` shows a `viewsWelcome` with `[Choose a base](command:deltaReview.setBranchBase)`. A missing explicit base skips the model: the tree is empty, `treeView.message` reads `⚠ Base <base> for branch <branch> does not resolve.`, context key `deltaReview.baseMissing` shows a `viewsWelcome` with `[Choose a base](command:deltaReview.setBranchBase)` and `[Use automatic detection](command:deltaReview.useAutomaticBase)`, the counter item hides, and the base item shows the error tint.
- **Status bar.** The new `baseStatusItem` sits left-aligned at priority 49, right after the counter (priority 50). Its text is `$(git-compare) ← <base>`, or `$(warning) ← <base>` while a stale prompt is unanswered, the base is missing, or no merge-base exists. A stale base whose prompt was answered or dismissed shows the normal text and tint. Background is `statusBarItem.warningBackground` while a stale prompt is unanswered, `statusBarItem.errorBackground` when missing or no merge-base exists. The command is `deltaReview.setBranchBase`. Text and tooltip come from a pure builder in `src/diffBaseUi.ts`. The counter tooltip becomes `Delta Review: <branch> vs <resolved base>`.
- **Picker** (`src/basePicker.ts`, UI only; items from `src/diffBaseUi.ts`):
  - Command "Delta Review: Set Diff Base for Branch" (`deltaReview.setBranchBase`) opens a QuickPick with sections `suggested` (detected fork point, upstream, fallback), `local branches`, then `Enter a ref…` and `Use automatic detection` (the latter only with an explicit base).
  - The current base is marked `$(check)`. A typed value matching no item adds `Use ref '<typed>'`. `Enter a ref…` opens an InputBox validated as the user types (`'<ref>' is not a valid ref in this repository.`).
  - Picking writes the contract file. "Use automatic detection" deletes it. Both refresh.
  - On detached HEAD the command shows `Delta Review: detached HEAD has no branch to set a base for.`.
- **Stale prompt.**
  - When `resolution.stale` is true and the pair is neither suppressed nor already prompting, show a warning: `Base <base> is fully merged into <fallback>. Switch the diff base for <branch> to <fallback>?` with actions `Switch to <fallback>` / `Keep <base>` / `Choose…`.
  - Switch writes the fallback as explicit. Keep writes the old base as explicit and suppresses the pair. Choose… opens the picker with the fallback first. Dismissal, or a cancelled Choose…, suppresses the pair.
  - Suppression is `context.workspaceState` key `deltaReview.staleBaseDismissed`: `{ [commonDir + "\0" + branch]: base }`. A different base for the branch un-suppresses. A pick in the picker also suppresses its own pair, so knowingly choosing a merged branch never prompts.
- **Base-side notes** go outdated through the existing merge-base logic, with no warning (decided).
- **Docs.** `plugin/skills/cluster/SKILL.md` gets a Contract "Diff base" section: file format, set/clear commands, and the resolution order with a shell snippet reproducing detection exactly. Workflow step 1 references it. README Settings and Usage, and DEVELOPMENT.md (lines 29, 74, 256-262 plus a "Diff base" subsection) move to the per-branch model. `deltaReview.baseBranch` stays as the fallback; its `package.json` setting description says so.

### Responsiveness

- **Compare-and-set** (`src/reviewState.ts`):
  - `writeSnapshotTree` takes the commit it read (`expectedOld: string | undefined`) and runs `git update-ref <ref> <new> <old>`, with `""` for "must not exist" (verified: git rejects with "reference already exists" / "is at X but expected Y"; a concurrent writer holding the lock gives "cannot lock ref … File exists").
  - `expectedOld` is the commit the mutation itself read at its start (`readSnapshotWithCommit` returns `{ state, commit }`, commit first, then `ls-tree <commit>`). `markReviewed` / `unmarkReviewed` / `clearAllReviewSnapshots` pass that commit straight to `writeSnapshotTree`; nothing re-reads the ref between the read and the write. `writeReviewState` (a lone write with no prior read) keeps its signature and reads inside.
  - A failed update-ref throws `ReviewStateConflictError` with `kind: "moved"` when the ref now differs from `expectedOld`, or `kind: "locked"` (with `lockPath`) when the error is `cannot lock ref … Unable to create '<path>.lock': File exists`. Anything else rethrows unchanged.
  - Every public mutation re-reads and retries its whole read-modify-write up to 3 attempts, waiting 50 ms then 200 ms before retries (injectable delay), then rethrows the last conflict. A lock that persists through all attempts may be a stale lock left by a crashed git process, so the "locked" kind never claims another window wrote.
  - The `refs/review-slices` anchor is unchanged: it is rebuilt from each refresh's own set.
- **Refresh scheduling** (`src/refreshScheduler.ts`, vscode-free):
  - `createRefreshScheduler({ delayMs: 400, maxWaitMs: 1500, run, timers })` gives a trailing debounce that fires at most `maxWaitMs` after the first unserved `schedule()`.
  - `isSelfWriteEventPath(path)` is true for paths with a `/.git/` segment followed by `refs/review`, `logs/refs/review`, or a `*.lock` of those. The repo watcher (`src/extension.ts` `watchRepo`) drops such events.
  - `headFingerprint(state)` covers HEAD name and commit. Git `state.onDidChange` schedules a refresh only when the active repo's fingerprint changed (`GitRepository.state.HEAD` typed in `src/gitExtensionApi.ts`).
  - Focus, save and config events go through the scheduler unchanged.
  - Trade-off: another window's mark on the same branch shows on the next focus, save or HEAD change rather than instantly.
- **Optimistic marks** (`src/optimisticModel.ts`, pure): `withReviewStatus(model, paths, reviewed)` returns a copy with those files' `status` / `hasReviewSnapshot` set. `revertReviewStatus(model, prior)` restores captured `{ path → { status, hasReviewSnapshot } }`.
  - `applyReviewStateChange(action, mutate, optimistic?)` publishes the optimistic model (tree, badge, counter) before enqueueing, with no `withProgress`. On success it refreshes. On failure it reverts on the current model, refreshes, and shows `Could not <action> <subject>: <reason>. Your mark was undone.` with `Retry` (re-runs the command's change) and `Show Log` (new OutputChannel "Delta Review", which receives the full error). Reasons: conflict `moved` reads `the review state changed in another window and the retry also failed`; conflict `locked` reads `<ref> stayed locked by another git process (<lockPath>); if no git command is running, delete that file`; anything else is git's reason from pure `gitErrorReason(error)` (`src/optimisticModel.ts`): the first stderr line starting `fatal:` or `error:` with that prefix and a trailing period stripped, else the first non-empty stderr line, else the message's first line. `git.run` rejects with Node's raw execFile error, whose message starts `Command failed: git …`; stderr comes from its `stderr` property (Buffer or string), falling back to the message lines after the first.
  - Pending overlay (the only rule keeping in-flight refreshes from flipping a row back): each optimistic change registers `{ token, paths, reviewed }` in an ordered `pendingMarks` list before its publish. Every refresh applies all pending entries (in order, via `withReviewStatus`) to its computed model before resolving clusters and publishing, so a refresh that read pre-write state at any point (including one queued behind slice anchoring) still shows the optimistic rows. When the write settles, the entry is removed and `refresh()` is called in the same synchronous step; that call bumps `refreshGeneration` at its start, so any older refresh bails before publishing un-overlaid state.
  - `publishModel(model)` sets `model`, re-resolves `clusterModel = resolveClusterModel(clusterContract, model.files)` when the last refresh had a valid contract (`clusterContract`, stored by `refresh()`), then sets the tree, badge and counter. Grouped (cluster) rows therefore move with the optimistic publish and the revert. `publishCount` (exposed on `__inspect`) counts refresh publishes only: it increments in `refresh()` beside its `publishModel` call, never inside `publishModel`, so the optimistic publish does not count and a mark adds exactly one.
  - Applies to file, folder, cluster, auto, mark-all and unmark-all.
- **No-op reasons**:
  - Mark or unmark with no model, from pure `noModelMessage` (`src/optimisticModel.ts`) fed by `reviewUnavailable`, which `refresh()` sets at the missing-base return and the `MergeBaseError` path and clears on every other outcome:
    - still loading: `Delta Review: the review is still loading — try again in a moment.`
    - base missing: `Delta Review: nothing to mark — base <base> for branch <branch> does not resolve. Click the base in the status bar to choose one.`
    - no merge-base: `Delta Review: nothing to mark — no merge-base with "<base>". Click the base in the status bar to choose another.`
  - Mark or unmark on a non-file element: `Delta Review: select a file row to mark it reviewed.`
  - Unmark without a snapshot: `Delta Review: <path> has no reviewed snapshot to drop.`

### Notes from the pane

- **Contract v3** (`src/notes.ts`):
  - Types are `Note` (existing line/document note, unchanged), `FileNote = { scope: "file", id, file, contentBlob, turns, status, outdated, createdAt }`, `GeneralNote = { scope: "general", id, turns, status, outdated, createdAt }`, and `AnyNote = Note | FileNote | GeneralNote`. `NotesFile.notes: AnyNote[]`, `version: 1 | 2 | 3`.
  - Only version 3 reads `scope`. A scoped note carries no `side`, line fields, `snapshot`, `document` or `appliedAnchorAt`. A general note also has no `file` and no `contentBlob`.
  - `notesFileVersion` returns 3 if any scoped note, else 2 if any document note, else 1.
  - Code term: "scope". User-facing term: "General note" / "File note".
- **Threads** (`src/noteThreads.ts`): `NoteThread<N extends AnyNote = Note>`, `AnyNoteThread = NoteThread<AnyNote>`. `mergeThreads` returns `AnyNoteThread[]`, with guards `isLineThread`, `isFileThread`, `isGeneralThread`. Scoped threads never get `effectiveAnchor` applied: a response `anchor` on them is ignored.
- **Store** (`src/notesStore.ts`):
  - `createNote` accepts `NoteDraft | FileNoteDraft { scope: "file", file, content, text, id? } | GeneralNoteDraft { scope: "general", text, id? }`. The optional pre-allocated `id` lets the general-note tab and the file-note draft adopt their thread.
  - `anchorBlobs` anchors every note that has a `contentBlob`.
  - `refreshDerived` skips scoped notes in anchor application. A file note's `outdated` = `!isInReviewSet(file)` (new optional `RefreshOptions.isInReviewSet`, defaulting to "working content exists"). A general note keeps `outdated: false`.
- **File-note threads** (`src/commentController.ts`, `src/noteTarget.ts`):
  - `fileNoteTargetFor(model, note, onDisk)`: a model file that is deleted → its base document; on disk → working file; else → base document at `contentBlob`.
  - The thread is created at `Range(0,0,0,0)`, then `thread.range = undefined` (a file-level comment above line 1).
  - `startFileNoteDraft(uri: vscode.Uri, path: string, noteId: string)` creates an empty, expanded, range-less thread with `contextValue = "fileNoteDraft"` and tracks it in `fileNoteDrafts: Map<CommentThread, { path, noteId }>`. `addNote` saves a thread found in `fileNoteDrafts` as a file note with that `noteId`.
  - New comment-thread command `deltaReview.cancelNoteDraft` (when `commentThread == fileNoteDraft`) disposes it.
  - The thread label is `whole file`. General notes never render as comment threads.
- **General-note tab** (`src/generalNotePanel.ts` vscode UI, `src/generalNoteHtml.ts` pure HTML):
  - One `WebviewPanel` per note id, reused (`reveal`), titled with the first line truncated, icon `$(comment-discussion)`. It holds a header (first line, status, Resolve/Unresolve, Delete), a meta line (`General note · branch <b> · created <date>`), turns (markdown via `markdown.api.render`, escaped-text fallback), Mark Read when pending-unread, and a reply box.
  - Draft mode (`New General note`, `Not tied to a file · branch <b>`) shows Add Note / Cancel. Add Note creates the note with the panel's pre-allocated id and retitles. Cancel closes.
  - Strict CSP with a nonce. Reply text survives re-render through `vscode.setState`.
  - Each panel records `{ repoRoot, storeBranch, key }`: `storeBranch` is the raw branch the notes store is called with (the same `computed.branch` that `refreshDerived` uses), `key` is `{ repo, branch: readMarkBranch(storeBranch) }`, the same shape and value as `notesKey`. It acts on those, never the active repo. On each successful notes render the panels whose `key` equals `notesKey` by value update, and close if their note is gone.
- **Pane** (`src/notesGrouping.ts`, `src/notesTreeProvider.ts`):
  - Groups are `{ kind: "general", threads }` first (label `General notes`, icon `comment-discussion`, collapse key `notesGeneral`), then branch overview, cluster notes and code groups as today.
  - Within a file group, file notes (by `createdAt`) come before line notes (by `currentStartLine`). File rows have description `file` (plus `⚠` if outdated). General rows have no description, and their command is `deltaReview.openGeneralNote`. Row actions are unchanged.
  - Clear Resolved covers every thread. Its archive entries are the removed notes exactly as they stood in the notes file, so file and general notes enter the archive scope-shaped (no `snapshot`).
  - Welcome text becomes: `No review notes on this branch.\nClick + above to add a file or general note, or hover a line in a review diff and click + to add a line note.`
- **Create** (`deltaReview.newNote`, `$(add)`, `view/title` `navigation@-1` on `deltaReviewNotes`): the QuickPick offers `File note` (description: path, detail `whole-file thread at the top of the diff`) and `General note` (`not tied to a file`). Availability comes from pure `fileNoteAvailability(active: { scheme, fsPath, path } | undefined, repoRoot, files: { path, deleted }[], baseScheme: string)` (`src/newNoteChoice.ts`; `extension.ts` passes the active tab's URI fields, the model's files and `REVIEW_BASE_SCHEME`), which returns `{ path } | { reason }` with these reasons:
  - `No file is open in the editor`
  - `<path> is not changed on this branch`
  - `<path> is deleted on this branch`
  - `Open a file from the Delta Review diff`

  A disabled item cannot be accepted, and the active item starts on General note. File note opens the diff and starts the draft. General note opens a draft tab.
- **`openNoteInDiff`** for a file note opens the diff (no selection) and expands the thread. Off the review set it opens the file-note target document.
- **Archive stays version 1** (decided). The archive's shell (`{ version, notes }`) is unchanged and its parser validates only the shell; entries were always "the note as it stood in the notes file plus `deletedAt`", which already admitted v2 document-note shapes without a bump. SKILL.md's archive section is amended: entries take any notes-file note shape; a line note's text record is `snapshot`, a scoped note's is its `turns` (plus `file` for a file note). The Schema-changes rule gains that archive entries follow the notes-file schema and need no archive bump of their own. `archiveNotes` takes `readonly AnyNote[]`.
- **Docs.** `plugin/skills/review-notes/SKILL.md` covers v3, `scope`, file and general note semantics, ignored anchors, and work-set order (general first, then by file with file notes before line notes). README and DEVELOPMENT.md cover the notes pane.

## Hard-to-undo

- Notes file schema version 3 (`notes-<branch>.json` written at `version: 3` once a file or general note exists). Extensions without v3 support reject such a file. This is a public contract change in `plugin/skills/review-notes/SKILL.md`.
- Review-note archive (`archive-<branch>.json`, append-only) receives scope-shaped file/general note entries while staying `version: 1`. Once appended they cannot be rewritten; the archive contract text in `plugin/skills/review-notes/SKILL.md` changes accordingly.
- New public agent contract file `<git common dir>/delta-review/base-<sanitized-branch>.json` (version 1, fields `branch` and `base`), documented in `plugin/skills/cluster/SKILL.md`, written and deleted by the extension.
- `refs/review/<branch>` and `refs/review-predeletion/<branch>` writes switch to compare-and-set with retry. The data format is unchanged, but the writes go to persistent shared state.
