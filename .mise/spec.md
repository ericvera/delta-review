# Spec: moved files inherit review across split/overwritten origins; combined cluster diff

## What

1. A declared (or detected) whole-file repo move inherits its old path's reviewed snapshot in two cases that are blocked today:
   - Extraction entries (`fromLines` set) naming the same `from` no longer make the origin "shared". Only whole-file moves (`fromLines === undefined`) count toward the shared-origin rule.
   - The origin may be its own row in the review set when that row is only its deletion (the path is in the review set and absent from the working tree). A `from` that is its own row and still exists on disk (including a case-only rename seen through a case-insensitive filesystem) still blocks inheritance.
   - Marking the origin's deletion row reviewed does not cancel the inheritance: the moved file keeps diffing against the snapshot it inherited and still reads Needs Review; the deletion row reads Reviewed on its own (goals Decision 1).
   - Unmarking a moved file that inherits still drops the origin's key, so an origin deletion row is unmarked with it (goals Decision 2, accepted).
   - Trade-off: an overwrite destination that inherits diffs against the inherited snapshot (a snapshot outranks the merge-base blob), so the content it overwrote is no longer shown anywhere.
2. A new cluster-row command **Open Cluster Changes** (`$(diff-multiple)`) opens every file of the cluster that needs review in VS Code's multi-diff editor (`vscode.changes`), each against its own base (reviewed snapshot where one exists, otherwise the base the single-file diff uses), titled `Cluster Changes: <label>`, or `Cluster Changes: <label> (<n>)` (n = 1-based cluster index) for a real cluster whose label another bucket shares. It shows on any cluster row with at least one needs-review file (real clusters, Unclustered, Auto), first inline and first in the context menu. If nothing needs review at click time, an info message reads `No files in '<label>' need review.`
   - The combined diff's editor title bar offers **Mark Cluster Reviewed** (`$(check-all)`, first), which marks the files the tab shows that still need review. If the cluster behind the tab has changed since it opened (its label or title no longer matches, or the active repo or branch is no longer the one the tab was opened from), it marks nothing and shows `Cluster '<label>' changed since this diff opened. Reopen it from the Delta Review pane.` The tab stays open and is not refreshed: its diffs keep the bases they opened with.
   - While the combined diff is the active tab, moving the cursor into a file's text on either side (click or keyboard) selects that file's row in the Delta Review pane without taking focus; nothing happens when the pane is hidden/collapsed, or when the row is already selected. Ordinary editors and single-file diffs do not move the selection.

## Design

### Task 1: inheritance rules (`src/model.ts`)

- `fromCounts` in `computeReviewModel` counts only moves with `fromLines === undefined`. `originShared` keeps its meaning: "more than one whole-file move resolved for the review set has this `from`".
- `selectReviewSnapshot` input `reviewPaths: ReadonlySet<string>` is replaced by `liveReviewPaths: ReadonlySet<string>`: review-set paths present in the working tree (the keys of `currentShaByPath`). The condition `!input.reviewPaths.has(move.from)` becomes `!input.liveReviewPaths.has(move.from)`. The `originDeleted` pre-check in `computeReviewModel` uses the same set. The diff-base precedence comment (`src/model.ts:318-320`) and DEVELOPMENT.md manual step 18 state the overwrite trade-off from What §1. `isAbsentAtExactCase` stays in the pre-check unchanged. Case-only-rename guard: on a case-insensitive filesystem a case-renamed `from` that is its own row passes `existsSync`, is hashed into `currentShaByPath`, is therefore live, and is rejected.

### Task 1: pre-deletion snapshots (Decision 1)

- New sibling ref `refs/review-predeletion/<branch>`. Its tree maps path to the snapshot blob that path held in `refs/review/<branch>` just before its deletion was marked reviewed (the moment the sentinel overwrote it). It uses the same tree format as the review ref (`100644 <sha> 0\t<path>`, commit chain with parents).
- `src/reviewState.ts`:
  - Generalize the existing read/write into ref-parameterized helpers (`readSnapshotTree(git, ref)`, `writeSnapshotTree(git, ref, map)`). `readReviewState` / `writeReviewState` become thin wrappers. Add `preDeletionRefForBranch(branch)` and `readPreDeletionState(git, branch)`.
  - `markReviewed`: for each deleted path P being marked, when the review state's prior value for P is defined and is not the sentinel, record `pre[P] = prior`. When the prior value is already the sentinel, leave `pre[P]` as it is. When the prior value is undefined, delete `pre[P]`. For each existing path being marked, delete `pre[path]`. Write the pre-deletion ref only when the map changed.
  - `unmarkReviewed`: also delete `pre[path]` for every unmarked path, and write only when changed.
  - `clearAllReviewSnapshots`: reads both maps and checks each independently: it writes an empty review tree when the review state is non-empty, then an empty pre-deletion tree when the pre-deletion map is non-empty. The existing early return on an empty review state must not skip the pre-deletion check (a failed second write can leave `pre` entries behind an empty review state).
- Write order: `markReviewed` writes the pre-deletion ref before the review ref (a failed second write then leaves an extra `pre[P]`, which only matters while P holds the sentinel, and re-marking repairs it). `unmarkReviewed` writes the review ref first.
- `src/model.ts`: new exported pure helper `originSnapshotSha(from, reviewState, preDeletionState, sentinelSha)`. It returns `reviewState.get(from)`, except that when that value is the sentinel it returns `preDeletionState.get(from)` (possibly undefined). `selectReviewSnapshot` gains input `preDeletionState: ReadonlyMap<string, string>` and computes `inheritedSha` with the helper. The `!== sentinelSha` check stays as a guard. `computeReviewModel` reads `readPreDeletionState` and uses the helper for `oldSha` in the `originDeleted` pre-check. The deletion row's own status is unchanged (own === sentinel === currentSha means Reviewed).
- `src/extension.ts` `deltaReview.clearReviewState` also deletes `refs/review-predeletion/<branch>` (like `deleteSliceRef`).
- `README.md:10` (the list of refs the extension writes) gains `refs/review-predeletion/<branch>`.
- The resulting behavior: marking deletion row P writes the sentinel to P and saves X to `pre[P]`, and moved file F keeps inheriting X. Unmarking F drops F, P and `pre[P]` (Decision 2). Unmarking P drops P and `pre[P]`, so F stops inheriting. That coupling already existed before this change. An older sentinel with no snapshot behind it still blocks inheritance.

### Task 2: combined cluster diff

- New VS Code-free module `src/clusterChanges.ts` (+ `src/clusterChanges.test.ts`):
  - `clusterLabelForKey(model: ClusterModel, clusterKey): string` returns `"Unclustered"`, `"Auto"`, or the bucket label (`""` when unknown).
  - `clusterChangesFiles(files: readonly ReviewFile[]): ReviewFile[]` returns the needs-review files in the given (path) order.
  - `clusterChangesTitle(model, clusterKey): string` returns `` `Cluster Changes: ${label}` `` for synthetic keys and for real clusters whose label equals no other key's label (other real clusters, `"Unclustered"`, `"Auto"`); those titles are reserved first. Each real cluster `c<i>` with a colliding label then gets, in index order, `` ` (${n})` `` with `n` starting at `i + 1` and incremented while that title is already reserved or assigned. Titles are thus unique within one model, even when a label looks like a suffixed title.
  - `clusterChangesMarkPaths(entry: { title; label; paths; repoRoot; branch }, current: { title; label; repoRoot; branch }, clusterFiles: readonly ReviewFile[]): { paths: string[] } | { message: string }`. When any of `label`, `title`, `repoRoot`, `branch` differs between `current` and `entry`, returns the changed-cluster message.
  - `sameClusterChangesSource(entry: { repoRoot; branch }, current: { repoRoot; branch }): boolean` is true when both match; `clusterChangesMarkPaths` and click-to-select use it. Otherwise returns the needs-review files of `clusterFiles` whose path is in `entry.paths`, or `nothingToReviewMessage(label)` when none are left.
  - `nothingToReviewMessage(label): string` returns `` `No files in '${label}' need review.` ``.
  - `fileForDiffDocument(files, doc: { scheme: "file" | "base"; path: string; query?: string }): ReviewFile | undefined` resolves an editor document to the file whose diff shows it. `"file"` with a repo-relative path matches `file.path` (non-deleted files). `"base"` with path and query matches either `diffBasePath === path && (diffBaseSha ?? "empty") === query`, or a deleted file's right side (`path === file.path && query === "empty"`). The first match in list order wins.
- `src/extension.ts`:
  - Extract `diffUris(file): { left: vscode.Uri; right: vscode.Uri }` from `openDiff`; `openDiff` uses it.
  - `deltaReview.openClusterChanges(element: cluster)` resolves the files with `clusterFilesForKey` and `clusterChangesFiles`. When none are left it shows the info message. Otherwise it closes every open combined-diff tab carrying `title` (helper `clusterChangesTabsFor(title)`: tabs across `window.tabGroups.all` whose `label === title` and whose `input` is not a known stable input class, see below) with the stable `window.tabGroups.close(tabs)`, and returns without opening when that resolves `false`. Only then does it record `title -> ClusterChangesEntry { clusterKey, label, paths, leftSides, repoRoot: git.repoRoot, branch: model.branch }` (`leftSides`: per shown file, `{ path, basePath, baseQuery }` = its file path plus the left URI's path without leading `/` and its query, as opened; the tab's left documents keep that identity even after the model's `diffBaseSha` changes) in an in-memory `clusterChangesTabs` map and run `vscode.changes(title, files.map(f => [Uri.file(abs f.path), left, right]))`. Rule: at most one combined-diff tab exists per title, so a map entry always describes the one tab carrying its title (`vscode.changes` creates a new tab on every call).
  - Active-tab tracking: a helper `activeClusterChanges()` reads `window.tabGroups.activeTabGroup.activeTab`. It matches when the tab's `input` is not one of the known stable input classes (`TabInputText`, `TabInputTextDiff`, `TabInputCustom`, `TabInputWebview`, `TabInputNotebook`, `TabInputNotebookDiff`, `TabInputTerminal`) and its `label` is a key of `clusterChangesTabs`; it then returns the full `ClusterChangesEntry`. On `tabGroups.onDidChangeTabs` and `onDidChangeTabGroups`, `setContext("deltaReview.clusterChangesActive", activeClusterChanges() !== undefined)`. Pruning: on `onDidChangeTabs`, for each label in `event.closed` only, delete its map entry when `clusterChangesTabsFor(label)` is empty. Opened or changed tabs never prune, so an entry recorded just before its tab exists survives.
  - `deltaReview.markClusterChangesReviewed` (editor title, `when: activeEditor == 'multiDiffEditor' && deltaReview.clusterChangesActive`, group `navigation@-1000`) first resolves the tab it was invoked from (`activeEditor` in an `editor/title` `when` is evaluated per editor group, but the context key is global, so in a split layout the button can show in another group's multi-diff). If the arguments VS Code passes to an `editor/title` command identify the group/tab (the implementer confirms what a multi-diff editor passes), that tab must be our combined diff (non-stable input, label a key of `clusterChangesTabs`) and must be the active tab of the active group, else it returns silently. If the arguments do not identify it, it refuses with `Can't tell which editor this button belongs to. Focus the cluster's combined diff and try again.` unless the active tab of the active group is ours, exactly one open tab carries its title, and no other group's active tab has a non-stable input. It then takes the entry and that tab's title. When `clusterChangesTabsFor(title).length > 1` it shows `More than one '<title>' tab is open. Close them and reopen it from the Delta Review pane.` and writes nothing (guard behind the close-before-open rule). Otherwise it captures `activeGit = git` and `branch = model.branch` once, computes `current = { title: clusterChangesTitle(clusterModel, key), label: clusterLabelForKey(clusterModel, key), repoRoot: activeGit.repoRoot, branch }`, and runs `clusterChangesMarkPaths(entry-with-title, current, clusterFilesForKey(clusterModel, key))`. A message is shown as info and nothing is written; paths are marked through the same `applyReviewStateChange` + `markReviewed` path as `markClusterReviewed` (shared helper taking explicit paths plus the captured `activeGit` and `branch`, so the write goes to the repo and branch that were compared).
  - Click-to-select: `window.onDidChangeActiveTextEditor`. When `activeClusterChanges()` is defined, `treeView.visible`, and `sameClusterChangesSource(entry, { repoRoot: git.repoRoot, branch: model.branch })`, it maps `editor.document.uri` (scheme `file` under the repo root to a relative path; scheme `REVIEW_BASE_SCHEME` to `{path without leading "/", query}`). A base document matching an entry `leftSides` item (`basePath` and `baseQuery`) resolves to the model file with that item's `path`; otherwise it goes through `fileForDiffDocument` over the model files whose paths are in the entry's `paths` (working sides and deleted files' right sides). It skips when `treeView.selection` already holds a file element with that path, otherwise calls the existing `revealFileRow(file)`.
- `package.json`: declare both commands. Add `openClusterChanges` to `view/item/context` (`viewItem =~ /^clusterNeedsReview/`, `inline@1` and `navigation@1`), change the existing cluster `markClusterReviewed` / `unmarkClusterReviewed` `navigation` entries to `navigation@2` / `navigation@3` (VS Code sorts by group, then order with missing = 0, then title), and add `markClusterChangesReviewed` to a new `editor/title` menu at `navigation@-1000` (a negative order sorts ahead of core's own `navigation` buttons). Hide both in `commandPalette` (`when: false`).
- Nothing is removed.

## Hard-to-undo

- New ref writes: `markReviewed`, `unmarkReviewed` and `clearAllReviewSnapshots` write commits to the new `refs/review-predeletion/<branch>` in users' repos.
- New ref delete: Clear Review State runs `git update-ref -d refs/review-predeletion/<branch>`.
- Review-state write from the combined diff: **Mark Cluster Reviewed** in the editor title bar overwrites each marked file's prior snapshot in `refs/review/<branch>` (`src/reviewState.ts:108`). Limited to files the tab shows that still need review, and refused when the cluster behind the tab no longer has the label and title it opened with, when the active repo root or branch differs from the one recorded when the tab opened (the write goes to the compared repo and branch only), when the invoking tab is not our combined diff or cannot be told apart from another group's multi-diff, or when more than one tab carries the tab's title. Opening a combined diff closes any open tab with the same title first, so at most one tab per title exists and the map entry always matches the tab the button is pressed in.
- Data delete (Decision 2, accepted): unmarking a moved file that inherits from an origin that is its own deletion row deletes that origin row's snapshot key (and its pre-deletion entry) from `refs/review/<branch>`; the row's mark is lost (the ref history keeps the old commit).
