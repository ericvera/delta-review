# Development

## Build & run

```bash
yarn install
yarn build     # or: yarn watch
```

The build is an esbuild bundle: `yarn build` typechecks with `tsc` (`noEmit`) and then bundles `src/extension.ts` into a single `out/extension.js` (CommonJS, node platform, sourcemap; runtime deps like `picomatch` are inlined, only `vscode` stays external — see `esbuild.mjs`). `yarn watch` runs the bundler only, without typechecking.

Open this folder in VS Code and press **F5** ("Run Extension"). An Extension Development Host window opens with the extension loaded — open any git repo with a feature branch in it and start reviewing.

## Packaging

```bash
yarn package       # produces delta-review.vsix (e.g. to share it)
yarn install-ext   # package + install into VS Code in one step
```

Run `yarn install-ext` again after any change to update; reload open windows (**Developer: Reload Window**) to pick up the new version.

## How it works

Review state is **content, not a flag**. Marking a file reviewed snapshots its current working-tree content as a git blob, anchored under a shadow ref (`refs/review/<branch>`). Three sibling refs anchor the other blobs the extension writes: `refs/review-notes/<branch>` (note snapshots), `refs/review-slices/<branch>` (origin slices for declared extractions), and `refs/review-predeletion/<branch>` (the snapshot a path held before its deletion was marked). A file's status is always derived by comparison:

- working tree content == reviewed snapshot → **Reviewed**
- snapshot exists but differs → **Needs Review**, and the diff opens against the snapshot (the delta since last review)
- no snapshot → **Needs Review**, diff opens against the merge base with the base branch
- moved file (git rename, or a declared `repo` move that won precedence) with no snapshot of its own → inherits the snapshot at its old path (`selectReviewSnapshot`, `src/model.ts`): the diff opens against it (`last reviewed ↔ working tree`), yet the file stays **Needs Review** until marked, since status reads the own snapshot only and a mark writes the new path only. An own snapshot outranks the inherited one; an inherited one outranks every other base. Not inherited when the move is `external`; it declares `fromLines`; another whole-file move shares its `from` (extractions naming it do not count; none of the whole-file moves inherits, so unmarking one never deletes a key a sibling relies on); the old path still exists on disk under its exact-case name, in the review set or not (a case-only rename counts as deleted, on a case-insensitive filesystem too); the old path is still its own row and exists on disk (a row that is only the old path's deletion, an overwrite, does not block it); or the old-path snapshot is the deleted sentinel with no pre-deletion snapshot behind it. Marking the origin's deletion row keeps the inheritance: the destination diffs against the snapshot the origin held before (`originSnapshotSha`, `src/model.ts`) and stays **Needs Review**, while the deletion row reads **Reviewed**. Unmarking the moved file drops the old path's snapshot too.

Because the state is content-based, it survives rebases, amends, and commits — nothing "resets" unless the file content actually changes.

`−` is the inverse of a mark, and it selects by **snapshot presence, never by status**:

- Every unmark — file row, folder, cluster, Auto subgroup, section header — drops the snapshot of every path in its scope whatever that path currently reads as, plus the old-path snapshot each moved file in it inherits (`reviewSnapshotPaths`, `src/model.ts`), so a file whose content diverged from its snapshot is one press away from the merge-base diff again. That is also why `−` renders wherever the scope holds a snapshot at all, needs-review rows included; a row that only inherits counts as holding one.
- The **Reviewed** header's `−` is scoped to the branch, not to the review set: it writes an empty state (`clearAllReviewSnapshots`, `src/reviewState.ts`), so snapshots for paths that have since dropped out of the review set go too, and the ref keeps its history. The palette's **Clear Review State** is the blunter tool — behind a modal it deletes `refs/review/<branch>`, `refs/review-slices/<branch>` and `refs/review-predeletion/<branch>` outright, leaving `refs/review-notes/<branch>` alone.
- Rows advertise that scope through their contextValue. `src/rowContext.ts` (pure, so the rule stays testable without `treeProvider`'s `vscode` import) appends `Snapshot` to the needs-review file, folder and Auto values — `needsReviewFileSnapshot`, `needsReviewFileDeletedSnapshot`, `needsReviewFolderSnapshot`, `needsReviewAutoGroupSnapshot` — and `clusterContextValue` (`src/clusters.ts`) returns `clusterNeedsReviewSnapshot`. Tokens append in a fixed order — status, then `Deleted`, then `Snapshot` — so the `Deleted` matches that hide **Open File** keep lining up. Reviewed rows carry no token: they always have a snapshot.

Deriving that status means content-hashing the working tree, which is what makes a refresh expensive on a large change. Two things bound it (`src/hashCache.ts`, `computeReviewModel` in `src/model.ts`):

- **Hash cache** — one `Map` per extension lifetime, path → `{ size, mtimeMs, sha }`. A refresh stats the review set and only sends the paths whose size or mtime moved to `git hash-object --stdin-paths`; a path with no stat vanished mid-refresh and is dropped rather than failing the whole batch. Both `computeReviewModel` calls in a `refresh()` share the instance, so the auto-mark recomputation re-hashes nothing. It is cleared on repository switch only — content identity is not branch-scoped — and a same-size write inside one mtime tick can leave a stale sha, the window git itself lives with; the next save's refresh heals it.
- **Scoped merge-base lookup** — `ls-tree` is limited to the paths the model can ask about (the review set, rename/move origins, declared destinations), batched at 500 pathspecs and sent with `:(literal)` magic so a filename containing `*`, `?` or `[` still matches. A pathspec that escapes the repo (an external move origin) is never sent.

Mark and unmark run inside `vscode.window.withProgress` on the view, so the queue wait, the ref write and the refresh that follows all read as busy rather than as a dead click.

Every write to the ref — inline `+`/`−`, the bulk and cluster actions, auto-marking, refresh-time slice anchoring, and Clear Review State — is serialized through one in-process queue (`src/serialQueue.ts`). Each mutation reads the ref, changes the path→blob map, and writes it back, so two overlapping writes would silently drop one side's paths. Only the mutation is queued, never the `refresh()` that follows it: refresh's auto-mark pass enqueues a write of its own and would deadlock behind a caller still holding the slot. A mark/unmark command that fails anywhere — the git write or that refresh — reports it as an error notification carrying git's stderr; the watcher-driven background refresh stays silent (it surfaces failures in the view's message banner as before).

### Where the state lives

Inside the repo's `.git` object database, under `refs/review/<branch>`:

- Never appears in the working tree, `git status`, branches, or PRs.
- Never pushed unless you explicitly `git push origin 'refs/review/*'`.
- Each save is a commit on the ref, so you get a browsable history of review sessions.
- `refs/review-slices/<branch>` is the sibling ref for declared extractions: the tree path is the blob's own sha, so the tree _is_ the anchored set. A refresh anchors its slice set before publishing its model, and one already superseded at its queue slot skips that; a commit lands only when the set changes; an empty set deletes the ref. Only slices the extension cut are anchored — a declared `baseBlob` whose content differs from the slice never enters the tree.

Inspect it:

```bash
git ls-tree -r refs/review/<branch>     # what's marked reviewed (path -> snapshot blob)
git log refs/review/<branch>            # review session history
git update-ref -d refs/review/<branch>  # nuke state for a branch (or use the command)
git ls-tree refs/review-slices/<branch> # origin slices anchored for declared extractions
git ls-tree -r refs/review-predeletion/<branch> # snapshots paths held before their deletion was marked
```

### Repository selection

Delta Review follows the repository selected in the Source Control view — the same selection that drives the built-in CHANGES panel. Switching to another repository or git worktree retargets the review set to that checkout (the panel header shows which one is active). If the built-in git extension is disabled, it falls back to the first workspace folder's repo. Review state is per-branch and lives in the shared `.git`, so it travels with a branch across worktrees.

### File status letters

Files carry `M`/`A`/`D`/`R` letters and colors like the CHANGES view — computed relative to `merge-base(baseBranch, HEAD)`, not HEAD, so committed changes still show. Untracked files are included.

Moves reach the model from two sources, made indistinguishable downstream by `adjustReviewSetForMoves` (`src/model.ts`):

- **Detected** — git's rename detection (`--find-renames`). Always a repo origin.
- **Declared** — a `moves` entry in the clusters contract; the only way a file ported from another project, or moved without git noticing, reads as a move. A declaration beats detection for the same path, and the displaced detected source re-enters the set as its own row. A declaration whose `path` is not in the review set is ignored.

Either way the file is a single `R` row at the new path:

- **Description** — `← <reduced origin> · verbatim|adapted|unchanged`, with `[donor]` before an external origin (`src/moveDisplay.ts`). The origin drops the trailing segments it shares with the new path, and an external origin is first cut back to its path inside the donor. Past `ROW_DESCRIPTION_THRESHOLD` (48 chars) it collapses to `…/<final segment>`. A **declared extraction** reads `← <origin filename>:<lines> · verbatim|adapted|unchanged` instead — nothing stripped, nothing shortened however long, and, when several ranges are declared, only the first plus `…` (`← big.ts:120-180…`). The tooltip stacks, in order: the full origin (`Moved from <path>`, plus `(donor: <name>)` when the donor is not already a segment of it; `Extracted from <path> lines 120-180, 200-210` for an extraction), the move note, the file's `notes` entry, the status line the next two bullets describe (`Unchanged since last reviewed` for an unchanged file), `Deleted from the working tree`, `Changed since last reviewed` (omitted for an unchanged file), then `Waiting on the agent: still expected to change.` (grouped mode, file in a waiting cluster or covered by `waitPaths`). The diff title follows the same vocabulary: `<name> (extracted from <path>:120-180,200-210 — merge base ↔ working tree)`, `moved from <path>` without lines.
- **`verbatim`/`adapted`/`unchanged` is derived, not declared** — `resolveFileBase` compares the working-tree blob to the last reviewed snapshot (own, else inherited) when there is one: `unchanged` if identical, else `adapted`. Otherwise it compares to whatever origin base resolved: the slice for an extraction, otherwise the declared blob or the whole origin file — `verbatim` if identical, else `adapted`. So `verbatim` only appears on a file with no snapshot, own or inherited; a move that cannot inherit keeps the origin comparison even when its old path has a snapshot. The tooltip's word for a verbatim match follows that base — `Identical to the extracted lines` when lines resolved, `Identical to the origin` otherwise. Two conditions, easily conflated: the row shows **no word** whenever that comparison is impossible (no snapshot and no origin base blob, or the file is deleted), while the tooltip's `Origin content is no longer available — showing the whole file.` needs the diff to have no base _at all_ — no origin blob, no reviewed snapshot, nothing at the destination's own merge-base path. So an overwrite with no snapshot and no origin blob, or a deleted move, drops the word without the line.
- **Diff base** — a reviewed snapshot, own or inherited, precedes everything below, with `diffBasePath` the file's own path. Otherwise an external origin uses the contract's `baseBlob`, kept only while `git cat-file -t` still reports a blob. A repo origin resolves in `src/originSlice.ts`, in order: the `fromLines` slice of the old path's merge-base blob (when no `baseBlob` is declared, or the slice matches it); else the declared `baseBlob`, with the origin searched line-aligned for where that content moved to, so the displayed lines are the ones it now sits at; else, with no `fromLines`, the declared blob or the old path's merge-base blob whole. Declared lines that no longer fit the origin fall back to the whole origin file, with `Declared lines are outside the origin. Showing the whole file.` in the tooltip — gated like the unavailable line above, so it appears only when nothing else supplies a base. Nothing resolvable → an empty base, so the diff shows the whole file. `diffBasePath` is the old path whenever the base really is that origin's content.
- **Overwrite** — when the destination itself existed at the merge base, its own blob wins as the diff base (an overwrite is still an edit to a file the reviewer already had), and the repo origin's `D` row is _not_ suppressed: the origin's content is shown nowhere else.

Rename detection only sees what git sees — a plain unstaged `mv` still shows as a `D` row plus an untracked `A` row until staged or declared.

### Base document identity

The left-hand side of a review diff is a virtual document served by `src/contentProvider.ts`. Declared moves made its identity non-obvious, so it is resolved in exactly one place (`src/baseDocument.ts`):

- `ReviewFile.diffBasePath` names whichever content the base side shows — a repo origin's old path when the base really is that origin's blob, the file's own path otherwise, external origins included. Always repo-relative, so a donor path can never escape into a URI, the notes contract, or a ref. `openDiff` and the comment controller read it; nothing re-derives the left-hand path.
- A base document is keyed by the pair `(diffBasePath, diffBaseSha)` — `reviewBaseUriParts` puts the path in the URI path and the sha in its query, so the same path at two blobs is two distinct documents. A missing sha reads as the empty document.
- Why the key changed: two review files can now present the same base path, by two routes. (1) A declared repo move whose origin is itself in the review set — suppression requires the origin to be deleted, so an origin still on disk _and_ independently modified (or untracked) keeps its own row; an unmodified copy source never enters the review set and collides with nothing. (2) Two declarations naming the same `from`, since `parseClustersContract` dedupes on `path` only. Git's rename detection allowed neither, because it always removed the source row.
- Base-side review notes therefore resolve their current base with `baseBlobForNote`: (1) a file showing that base path whose `diffBaseSha` is the note's own `contentBlob`; (2) else the sole file showing that path — this is what lets a note follow a base that advanced when its file was marked reviewed — with the `path === file` tiebreak when several show it; (3) else no current base.
- The provenance thread never reaches any of this: it lives on the right-side document only, so `baseBlobForNote` never sees it.

### Auto triage

Every file in the review set is classified `auto` or `normal` (`src/triage.ts`, called from `computeReviewModel` in `src/model.ts`) from exactly two inputs:

- `deltaReview.autoReview.globs` — picomatch patterns (`dot: true`, case-sensitive, repo-relative `/` paths). Empty, non-string, or uncompilable entries are skipped, never fatal.
- Paths marked `linguist-generated` in `.gitattributes`, fetched via `git check-attr --stdin -z linguist-generated` (best-effort: any failure means "none").

`auto` files render in the collapsed **Auto** subgroup (flat in both layouts, directory shown in the description) and are excluded from the normal list/tree and from folder bulk actions; group counts and Mark All still include them. With `autoReview.markAutomatically` on, `refresh()` marks needs-review auto files through the normal `markReviewed` snapshot path before the tree updates — so while the setting is on, an edited auto file is simply re-marked with a fresh snapshot on the next refresh and never resurfaces. Turn the setting off and the next edit resurfaces as a delta against the last snapshot, exactly like a hand-marked file.

### Clusters contract

Clustered review is driven by a JSON contract the extension only ever **reads** — an external tool (the `/delta:cluster` Claude Code skill in `plugin/`) writes it:

- Path: `<git common dir>/delta-review/clusters-<sanitized branch>.json`. The common dir (`git rev-parse --git-common-dir`, resolved against the repo root when relative) keeps the contract next to the review refs, shared across linked worktrees.
- Sanitization: every branch-name char outside `[A-Za-z0-9._-]` becomes `-` (`sanitizeBranchForFilename` in `src/clusters.ts`; the skill applies the identical rule).
- Schema: `{ "version": 4, "clusters": [{ "label", "summary", "files": [...], "patterns": [...], "wait" }], "moves": [...], "notes": { "<path>": "<one-liner>" | ["<one-liner>", { "text", "lines": [start, end] }] }, "levels": { "<path>": "review" | "skim" }, "waitPaths": ["<path>"] }` — each cluster needs at least one non-empty array of `files` (explicit repo-relative paths) or `patterns` (picomatch globs). Unknown keys are ignored. `parseClustersContract` returns one-line user-facing errors.
- Versions: the parser accepts the integer `1`, `2`, `3` or `4`; the `delta:cluster` skill writes `4` only when some `notes` value is an array (holds a ranged item), else `3`. Anything else fails the file with `unsupported version <v> (extension supports 1, 2, 3 and 4)`. A version 1 contract normalizes to an empty `moves` list, and a `moves` key inside one is ignored.
- `wait` (optional boolean on a cluster, any version; no version bump, since older extensions ignore it): `true` flags every member waiting; rendering follows the dim rule below. Non-boolean values reject the file. It gates no action and changes no order.
- `waitPaths` (optional top-level array of strings, any version; no version bump): repo-relative file or directory paths the agent still expects to change. Trailing `/` characters are stripped and entries left empty dropped; entry `e` covers path `p` when `p === e` or `p` starts with `e/`. A non-array or any non-string entry rejects the file with `"waitPaths" must be an array of strings`. Only members of real clusters are affected — `resolveClusterModel` records each bucket's covered members in `ClusterBucket.waitingPaths`, and entries covering Unclustered or Auto files do nothing. Covered members are flagged waiting; rendering follows the dim rule below.
- `moves` (version 2 and up, optional array): one entry per declared move — required `path` (the file's current repo-relative path) and `from` (the origin path), required `origin` (`"repo"` = elsewhere in this repo, `"external"` = another project); optional `donor` (non-empty project name, shown bracketed on the row), `baseBlob` (40- or 64-character lowercase hex object id holding the origin's content — on a `repo` entry, the declared lines concatenated, or with no `fromLines` whatever content the skill declared), `fromLines` (version 3 and up, `repo` entries only: a non-empty array of ascending, non-overlapping 1-based inclusive `[start, end]` pairs naming the origin lines this file was extracted from) and `note` (free text, shown in the tooltip).
- `notes` (version 3 and up, optional object): repo-relative path → a one-line remark for the reviewer (`ReviewFile.fileNote`). From version 4 a value may be an array whose items are strings (file-level, joined with one space) or `{ "text", "lines": [start, end] }` ranged remarks (integers, `1 <= start <= end`) that reach `ReviewFile.lineNotes`; a version 3 contract rejects an array value with the string-only message. Empty strings and empty-`text` items are ignored; entries naming a path outside the review set are ignored later, by the model.
- `levels` (optional object, any version; no version bump — ungated like `waitPaths`): repo-relative path → `"review"` or `"skim"`, reaching `ReviewFile.reviewLevel` (default `"review"`). A non-object rejects the file with `"levels" must be an object`, any other value with `levels["<path>"] must be "review" or "skim"`; keys naming a path outside the review set are ignored by the model.
- Silently dropped rather than fatal: `donor` on a `repo` entry, `baseBlob` on a `repo` entry below version 3, `fromLines` on an `external` entry, a `repo` entry whose `from` equals its `path`, and duplicate `path`s (first entry wins). A declaration whose `path` is outside the review set is ignored later, by the model.
- All-or-nothing: one malformed `moves` entry rejects the **whole** file, so declarations and clustering always fail together — a bad move declaration costs the reviewer their grouping too.

#### ClusterModel flow

- Every `refresh()` loads the contract exactly once (`resolveBranch`, then `loadClustersContract`), **before** the review model is computed. Its `moves` feed both `computeReviewModel` calls — the initial one and the auto-mark recomputation — and cluster resolution reuses that same parse, so a contract rewritten mid-refresh can never produce a model whose moves and clusters disagree.
- Contract states: `missing` → no cluster state, no message, no declared moves; `invalid` → the same, plus a `⚠ Clusters contract: <error>` view message; `ok` → the declarations reach the model and `resolveClusterModel(contract, files)` produces the grouping. An invalid contract costs declared moves as well as grouping.
- `resolveClusterModel` buckets the review set: auto-triaged files always go to `auto` (auto wins over everything); explicit `files` listings beat `patterns`, first listing cluster wins; otherwise the first cluster (contract order) whose pattern matches wins; the rest are `unclustered`. Files named by the contract but absent from the review set are simply not shown.
- Order inside a real cluster: explicit `files` members first, by their index in the first listing cluster's `files` array, then pattern-only members in path order. List mode renders that order (and the combined cluster diff follows it); tree mode sorts folders and direct files alphabetically (`treeLevel`). Unclustered, Auto, the Reviewed bucket and ungrouped mode stay path-sorted.
- The grouping lever (`deltaReview.groupByCluster` / `ungroupClusters`, workspaceState key `deltaReview.grouped`) only shows while a valid contract exists (`deltaReview.clustersAvailable` context key). Effective grouping is `preference && clusterModel !== undefined`, so a vanished/invalid contract falls back to ungrouped without erasing the preference.
- A dedicated watcher on `<common dir>/delta-review/*.json` schedules a refresh on contract create/change/delete; the per-refresh re-read keeps things correct even if watcher events are missed.
- Grouped rendering: clusters, **Unclustered**, and **Auto** show only their needs-review files; the Unclustered/Auto headers hide entirely while nothing in them needs review. An always-present **Reviewed** bucket renders last: check icon, plain count of all reviewed files, follows the list/tree toggle, no subgrouping; its contextValue reuses `reviewedGroup`, so its `−` is the same branch-wide clear as the ungrouped Reviewed header.
- Dim rule (grouped mode only; ungrouped renders unchanged): a row with nothing to review right now renders in `DIM_COLOR` (`gitDecoration.ignoredResourceForeground`). A real cluster header dims when every needs-review member is waiting (`clusterHeaderTone`) — so also when fully reviewed or empty — with a dim-colored icon. Its icon is `agent` instead of `layers` when the cluster is `wait` or a needs-review member is under `waitPaths`; the tooltip adds `Waiting on the agent: still expected to change.` for `wait`, else `Some files are waiting on the agent: still expected to change.` for the `agent` case. A cluster folder dims when every needs-review file under it is waiting (`everyFileWaiting`); a waiting file row dims with the wait tooltip line. The Reviewed bucket header (dim `check`), its folders, and its file rows always dim. Unclustered and Auto never dim. Folder and file icons come from the file icon theme and cannot be colored: only their labels and badges dim. Queries: file `<kind>` / `<kind>,wait` / `<kind>,dim`, folder and header `dim`; headers use `/header/<id>` paths so their decoration never lands on a file.
- A fully reviewed cluster keeps its header (`n/n`) with a single `All files reviewed.` row; cluster counts and header `+`/`−` still derive from the cluster's full membership.
- Reviewed-bucket folder `−` (tree mode) unmarks every visible child — auto files included, since they render inline in the bucket rather than in an Auto subgroup. With `markAutomatically` on, an unmarked auto file returns to Reviewed on the next refresh (standard auto-review behavior, for every unmark path).
- Grouping is pure presentation: tree rows resolve their files from the current `ClusterModel` at render time, and no lever flip touches `refs/review/<branch>`. Mark/unmark writes through the normal snapshot path, and that ref write is what moves a row between a cluster and the Reviewed bucket.
- Combined cluster diff tabs: the stable API has no multi-diff tab input class, so a tab is ours when its input matches no stable `TabInput*` class and its label matches a title recorded by `openClusterChanges`. Labels carry VS Code's localized ` (N files)` suffix once resources resolve, so every match goes through `isClusterChangesLabel`. The `deltaReview.clusterChangesActive` context key (updated on `onDidChangeTabs`/`onDidChangeTabGroups`) gates the title-bar **Mark Cluster Reviewed** button. A label matching more than one recorded title refuses to mark, as does a press while another group's active tab is also a non-stable-input page (the command's arguments cannot identify the group it was pressed in).

### Review notes

Inline notes on diff lines, threaded with an agent's replies. Three files per branch under `<git common dir>/delta-review/` (same dir and branch sanitization as clusters):

- `notes-<sanitized branch>.json` — **extension-owned**; created/edited from the diff editor. Agents only read it; the extension never rewrites an invalid one (corrupt → deduped warning, notes unrendered, mutations refused).
- `responses-<sanitized branch>.json` — **agent-owned**; the `review-notes` skill in `plugin/` appends `{ noteId, response, at, anchor?, pending? }` entries. The extension only reads it (corrupt → deduped warning, treated as missing). The skill's watch mode polls the notes file's content hash (not mtime) and recomputes the work set on every change, because derived-field write-backs after each refresh cause wakes with no new work.
- `archive-<sanitized branch>.json` — **extension-owned, append-only history**: Clear Resolved appends every note it removed, each the note object as it stood plus `deletedAt`, right after the notes-file rewrite and before but independently of re-anchoring (`archiveNotes` in `src/notesStore.ts`; shell parser `parseArchiveFile` in `src/notes.ts` validates only `version` and `notes`, since entries are opaque history). The extension never reads it for behavior of its own — only as the read half of the append. Unparsable → renamed aside to `<file>.corrupt-<stamp>` and a fresh archive started; unreadable or unwritable → nothing is appended and the existing file is left as it was. Either way a warning toast names what happened (`archiveWarning`) and the clear itself stands. Explicit deletes (thread or row Delete, only-turn deletion) never archive.

Types and whole-file parsers live in `src/notes.ts` (clusters semantics for the notes and responses files: one violating entry rejects the file with a one-line error); persistence and mutation in `src/notesStore.ts` (atomic same-dir temp+rename saves, an idempotence guard so identical saves never touch the file — no watcher loops — and load→modify→save helpers).

#### The ref: `refs/review-notes/<branch>`

Each note snapshots the whole noted document as a git blob (`contentBlob`, via `hash-object -w`). All live blobs are anchored by a commit on `refs/review-notes/<branch>` (tree path = note id → blob), so `git gc` cannot prune them. It is deliberately separate from `refs/review/<branch>`, `refs/review-slices/<branch>` and `refs/review-predeletion/<branch>`, the refs Clear Review State does delete: it must not destroy note snapshots. The ref is deleted when the last note goes. Notes removed by Clear Resolved drop out of the tree, so their blobs are no longer kept alive and `git gc` may prune them — the archive's `snapshot` is the surviving text record. Inspect with `git ls-tree refs/review-notes/<branch>`.

#### Anchoring model & derived-field refresh

A note pins `file`, `side` (`working` = right/current code, `base` = left/old code), a 1-based line range, the range's text (`snapshot`), and `contentBlob`. Every `refresh()` runs `refreshDerived` (`src/notesStore.ts`) to recompute the persisted hints (`status`, `outdated`, `currentStartLine/EndLine`):

- Diff `contentBlob` against the side's current content (`git diff -U0 <blob> <blob>`, hunks mapped by `src/noteAnchor.ts`): hunks above shift the range; a hunk touching it sets `outdated: true` and collapses it to one line; a missing document sets `outdated` and keeps the last position. A base-side note's current base comes from `baseBlobForNote` — the three-step lookup in [Base document identity](#base-document-identity) — so it progresses when its file is marked reviewed but never migrates onto a second file that happens to share the base path.
- Threads are merged in `src/noteThreads.ts`: reviewer `turns` + agent responses interleaved by `at`; status derived — explicit `resolved` wins, else last speaker (agent with `pending: true` → **pending**, other agent → **addressed**, reviewer → **open**); pending is persisted as `addressed` (`persistedStatus`) so older readers still parse the notes file. Derived fields are persisted back so agents reading the file get near-current hints.
- Pending read/unread is VS Code workspace state only (`deltaReview.pendingReadMarks`, logic in `src/pendingRead.ts`), never the contract files: keyed per repo root then branch — per repo because the extension follows the SCM-selected repo and all repos share one `workspaceState` — and per note to the newest agent turn's `at`, so a newer pending reply reads as unread again. Pruned on every successful notes load (zero-note loads included; never on an invalid or missing notes file), only inside the loaded repo's map, to present notes and that repo's existing local branches. Mark as Read re-styles in place (`restyleThreads` on the controller, `notesTreeProvider.setThreads`) and never calls `renderThreads`.
- Response anchors: the newest agent anchor that resolves (`buildAnchorResolver` — repo-relative `/`-separated path only, file exists, line in range; traversal/absolute paths are always dangling) relocates the note to the fix — side flips to `working`, file/lines/snapshot/`contentBlob` are rewritten and re-anchored on the ref. One-shot per response via `appliedAnchorAt`.
- The clusters watcher on `<common dir>/delta-review/*.json` also covers both notes files, so agent replies merge live without a manual refresh.

Rendering is the standard VS Code comments API (`src/commentController.ts`) — threads appear in the built-in Comments panel for free, nothing is built against it. The REVIEW NOTES section (`src/notesTreeProvider.ts`) is a sibling SCM view fed the same merged threads; `renderNoteThreads` in `src/extension.ts` fans out to both surfaces plus the view badge. Each note row also carries Resolve / Unresolve / Delete (Delete confirms first), which go straight to `src/notesStore.ts` — no diff and no rendered thread involved, so a note stays closable whatever happened to its file.

Two rendering invariants sit behind that, with their decisions in the vscode-free `src/threadRender.ts` so they are unit-testable:

- **A thread's reply box appears only on a freshly created thread.** VS Code builds a second reply button when an extension flips a live thread's `canReply` false→true (the lazily built form's async init and the accompanying thread update each create one), so `restyle` disposes and recreates the thread — with its comments, so the widget builds its form once at display. That drops an in-progress turn edit on that thread; accepted, since the typed text lives in the disposed widget either way.
- **`styleThread` writes only changed fields.** Every `comments`/`label`/`contextValue`/`state` write emits an update that could land on a form still initializing. Comment identity includes the **body kind** (raw string vs `MarkdownString`): handlers mutate comment objects in place, so the raw string an edit leaves behind is the only marker that the display body is owed a re-send.

#### The provenance thread

One read-only thread pinned above line 1 of every review file that has a declared move or a per-file note, carrying the origin line, the move note, the file note and the out-of-range warning (composition in the vscode-free `src/provenance.ts`; entries are `(path, deleted, body)`).

- **It is not a note.** It shares the `deltaReview.notes` controller — one controller is all the API offers — but lives in its own cache in `src/commentController.ts`, keyed by path, and is never registered in `threadNoteIds`. It is absent from the notes file, the REVIEW NOTES view, the view badge, and Clear Resolved, and no note-side sweep, restyle or re-clamp can reach it.
- **Read-only by construction.** `canReply = false` (the API default is `true`, and the controller's placeholder would otherwise offer a reply box), and neither the thread nor its single `Delta Review` comment gets a `contextValue` — every comment menu in `package.json` gates on one of `openNote`/`addressedNote`/`pendingNote`/`pendingNoteUnread`/`resolvedNote` or `reviewerTurn`, so it draws no actions.
- **File-level.** `createCommentThread` demands a `Range`, so it is created at `0,0` and then assigned `range = undefined`.
- **Rebuilt every refresh** from the model, beside `treeProvider.setModel` rather than inside `renderNoteThreads` — provenance comes from the clusters contract, so a notes file that fails to load leaves it standing. A body change rewrites `comments` in place; a URI change (a file becoming deleted) disposes and recreates, since thread URIs are immutable; a path that drops out of the entries is swept.
- `provenanceThreads()` on the controller returns a plain snapshot per rendered thread. It exists for the scripted extension-host check and nothing else.

#### Agent line threads

One read-only thread per ranged agent note (`ReviewFile.lineNotes`, version 4 contract), spanning its lines with the widget under the last one; entries come from `agentLineNoteEntriesFor` in `src/provenance.ts`. Same rules as the provenance thread (not a note, read-only, same right-side URI rule, rebuilt every refresh, cleared with it), except:

- **Ranged, not file-level.** The range is `start-1 .. end-1` at column 0 and is kept; clamped when the target document is open and re-clamped on open by `reclampThreadsFor`, so a range past the end sits on the last line. A range change writes `range` in place.
- **Own cache**, keyed `<path>\n<index>`, separate from both notes and provenance.
- **Label** `Agent note · lines a–b` (`line a` when single), one `Claude` comment with the escaped text, expanded.
- Plain-string notes still feed the provenance thread; the file row tooltip adds `<n> agent note(s) on lines: <ranges>`.
- `agentLineThreads()` returns a snapshot per thread (rendered 0-based range, label, read-only state, body) for the scripted extension-host check only.

#### Where a note's thread lives

`src/noteTarget.ts` (pure) decides the document a note attaches to, from `(model, note, workingFileExists)`; the thread and the REVIEW NOTES click both resolve through it, so the click always lands on the document the thread is on. Five cases:

- **Base-side note, any file** — the base document named by [Base document identity](#base-document-identity), falling back to the note's `contentBlob`.
- **Working side, file in the review set, not deleted** — the working file.
- **Working side, file in the review set, deleted** — that file's base document at `diffBaseSha ?? note.contentBlob`, never the empty document: a deleted file's diff has an empty right side, so only the base holds the noted content.
- **Working side, file absent from the review set, present on disk** — the working file; a real, editable file beats a historical snapshot.
- **Working side, file absent from both** — the note's own `contentBlob`, addressed in that blob's **creation** coordinates (`startLine`/`endLine`) rather than the working-tree-drifted `current*` pair.

The provenance thread is the one thread `src/noteTarget.ts` does not place: it always sits on the **right-side** document — the working file, or the empty base document standing in for a deleted file's missing right side — mirroring `openDiff`'s right-hand URI. It never lands on a base document, so a base snapshot never carries one. Like a right-side note's thread it also shows when the working file is opened outside a diff.

`reviewDiffIsEmpty` (same module) is the click path's escape hatch: a deleted file with no base blob diffs empty against empty, so instead of opening that diff the click opens the resolved target document directly.

An anchor can sit past the end of its target document, and clamping it needs a line count, which only exists once the document is open — so `src/extension.ts` re-clamps on `onDidOpenTextDocument` (file and `delta-review-base` schemes only). That listener must never call `refresh()` (git on every document open) or `renderThreads` (it disposes any cached thread absent from the array it is given, including the one `addNote` adopts before its refresh lands); it calls the controller's range-only `reclampThreadsFor`.

#### Long notes

Turns render as markdown (`commentsFor`, `src/commentController.ts`), in full, with no budget, truncation or escape hatch. Editing a turn swaps in its raw text (`NoteComment.turnText`).

- **No height trick.** Markdown rendering gives up `escapeMarkdownText`'s hard-line-break trick: a single newline soft-wraps and each paragraph adds its margin.
- **VS Code sizes the thread widget to its content** (≥ 1.98): the comment thread relayouts its zone to the measured content height without the zone widget's `max(12, 0.8 × editor lines)` cap, so a long thread grows past the viewport and the editor scrolls. The only remaining limit is per comment body — `max-height: 20em` with its own scrollbar, applied at comment-node construction while `comments.maxHeight` is not `false`.
- **The extension contributes `"comments.maxHeight": false`** (`contributes.configurationDefaults`, `package.json`) so the reviewer scrolls one thing, the editor. It is a window-wide default covering every comment provider (GitHub PR comments included); an explicit user setting overrides it.

## Manual test script

### Scripted extension-host checks

There is no committed e2e suite, but extension-host behavior can be verified headlessly with
`@vscode/test-electron`: a runner script calls `runTests` with `extensionDevelopmentPath` = this
repo root, a throwaway temp git repo as the workspace folder, and a short `--user-data-dir`
path; launch the runner with `env -u ELECTRON_RUN_AS_NODE`. The CommonJS suite drives the real
extension via `vscode.commands.executeCommand` and asserts on the contract files under
`.git/delta-review/`, the `refs/review*` refs, and rendered tree/thread state. Simulate SCM
repository switching via `git.toggleRepositoryVisibility` rather than the picker. With
`DELTA_REVIEW_TEST=1` in the launch's `extensionTestsEnv`, the extension registers one extra
command, `deltaReview.__inspect`, returning the review model's files, the provenance thread
snapshots (`threads`), the agent line thread snapshots (`agentLineThreads`), each file's row description, the REVIEW NOTES badge, the recorded combined-diff tabs and `treeRows` (every rendered tree row depth-first, collapsed or not: `id`, `label`, `description`, `icon`, `iconColor`, `query`) — state the public API does not
expose; it is absent from `contributes.commands`, so no shipped build offers it. These are
throwaway verification harnesses (session scratchpad), not shipped tests.

Basics (no contract, default settings):

1. In the dev host, open a repo with changes vs `main`. The panel lists them under Needs Review.
2. Click a file → diff is _merge base ↔ working tree_.
3. Click its `+` → it moves to Reviewed; status bar count updates.
4. Edit the file → it moves back to Needs Review, and its diff is now _last reviewed ↔ working tree_ (only the new edit). The row now offers `−` alongside `+`: press `−` → the snapshot is dropped and the diff is _merge base ↔ working tree_ again.
5. `+` to snapshot it again, edit it once more, then revert that edit (undo + save) → content matches the snapshot again, file returns to Reviewed on its own.
6. Commit / rebase — review state is unaffected (content-based).
7. Tree/list toggle, folder `+`/`−` (a Needs Review folder offers `−` too, once a child holds a snapshot), collapse state surviving reload, and repo switching in Source Control all behave as before.
8. Branch-wide reset: mark several files reviewed, then edit each of them → they all read Needs Review with delta diffs, and the **Reviewed** header shows `0` while still offering `−`. Press it → `git ls-tree -r refs/review/<branch>` prints nothing, every one of those files diffs _merge base ↔ working tree_ again, and `git log refs/review/<branch>` still lists the earlier sessions under the empty state.

Moves:

9. `git mv` a changed-or-unchanged file to another directory (pure move) → one **R** row at the new path, no row at the old path. Description `<new dir> ← <old dir> · verbatim`, with the origin's trailing segments shared with the new path dropped (in tree mode there is no directory text and the row starts at `←`); tooltip `Moved from <full old path>` then, a blank line later, `Identical to the origin`. Its diff says the files are identical, the title reads `<name> (moved from <old path> — merge base ↔ working tree)`, and the left editor is labeled with the old path. That last part holds for a repo origin only while the destination did not exist at the merge base (contrast step 18) and the file is not on a reviewed-snapshot base (contrast steps 11 and 15); step 16 covers an external origin.

Anchor relocation: append a response entry whose `anchor` names another file/line with that line's exact text as `snapshot` → the note relocates there (a base-side note flips to the working side) and the REVIEW NOTES row follows. An anchor with a bad path shape, a missing file, or an out-of-range line is ignored — reply still shows, note stays put. `snapshot` is not validated: a wrong-but-in-range anchor still relocates the note and stores that snapshot verbatim.
38. Outdated: edit lines **above** a note → the thread shifts down/up, not outdated. Edit the noted line itself → `⚠` in REVIEW NOTES and a dimmed `line was: …` in the thread's first comment.
39. Base progression: with a base-side note on a file, mark the file reviewed → the base thread is recreated against the new base (the reviewed snapshot); turns and status untouched.
40. REVIEW NOTES navigation: click a note → the file's review diff opens with the cursor on the noted line and the thread expanded. A note on a file no longer in the review set opens the plain file; if the file is gone from disk too, it opens the note's recorded content (`delta-review-base` at its `contentBlob`) at the line it was written on. Delete a noted file that is still in the review set → the diff's right side is empty as always, but the thread renders on the **left** (base) side, where the content exists, at the last line if its anchor ran past the end. A file **added** on the branch and then deleted has no base blob either, so its diff is empty on both sides — the click skips the diff and opens the note's target document directly. Resolve from the row closes it in every case.
41. Selection sync: collapse the DELTA REVIEW groups (and its folders, in tree mode), then click a note row → the noted file's row is revealed and selected with its ancestors expanded, while focus stays on the diff. Those ancestors persist across reload exactly like a manual expand. Same in all four layouts (list/tree × grouped/ungrouped); a note on a file no longer in the review set leaves DELTA REVIEW untouched.
42. Clear Resolved (view title `$(clear-all)`) → resolved notes vanish from the file, the threads, and the ref, and `.git/delta-review/archive-<branch>.json` now holds them with `deletedAt`; open/addressed notes untouched; clicking again is a no-op (file mtime unchanged) and adds nothing to the archive.
43. Branch switch: `git switch` to another branch → that branch's own (empty or different) notes render; switch back → the originals return. Review marks and notes stay per-branch.
44. Corrupt files: garbage in the notes file → warning toast, notes unrendered, note actions refuse, and the extension **never rewrites the file**; restore it → everything returns. Garbage in the responses file → warning, notes still render (without replies), recovers when fixed. Each warning shows once, not per refresh.
45. Comments panel: open the built-in Comments panel → the same threads are listed there via the standard API; review tree, clusters, and auto-review behave exactly as before while notes exist.
46. Long note: add a note whose text runs 30+ lines → the whole note renders inline and the thread expands to fit it; no text is clipped, the thread carries no truncation link and no title-bar button beyond resolve/delete, and the only scrollbar is the editor's — scroll down to reach the file's lines below the widget. Edit that turn → the editor opens on the same full raw text (that editor scrolls once it passes ~500px; that is not clipping) and saving preserves it. Blank lines inside a note still separate paragraphs, and long lines still wrap rather than scrolling sideways. `**bold**` and inline code in a note or reply render formatted.
